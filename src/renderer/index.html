    GUIDED DIAGNOSIS / READ-ONLY

    What would you like to investigate?

    Start with the evidence you can access. Add client logs or snapshots only when they help answer the next question. All analysis stays local; the app never controls playback or changes Emby settings.

    1. Check playback logs without access to the device
    1. Note the incident time and time zone. Collect the Emby server log and matching FFmpeg logs, if transcoding occurred.
    2. Choose a source: select local logs, or download them using a saved Emby connection. API log retrieval requires an administrator credential.
    3. Analyze the files. Review server requests, responses and session findings. A playlist HTTP 200 does not prove audible playback.
    4. If the client-side cause remains unknown, continue with the mobile device test. Server Debug logging is only needed for a short repeat when normal logs lack relevant request details.

    API prerequisite: select or create a connection and save its API key in Settings. Local files need no connection.

    2. Test a mobile device / add Android evidence
    1. Enable diagnostic logging in the Android app before testing. The server API cannot retrieve Android app logs.
    2. Record network, app version, audio and video quality settings separately. Start with the same album and play at least three titles; record manual skips versus automatic transitions and exact times with the time zone.
    3. Export the Android app log promptly and attach it below. Keep matching server logs selected to analyze both sources together; an Android-only analysis is also possible.
    4. Review the client evidence and possible workarounds. Change one setting at a time, restart the app, repeat, and verify the actual requested audio bitrate in the new log. Keep the original value so you can restore it.

    A repeated container-parsing error with HLS recovery can suggest an audio-quality comparison, not a universal 4 Mbps fix. Higher audio limits may use more mobile data and are not sufficient for every source bitrate. Enable server Debug logging only if a specific evidence gap calls for it; disable it after the repeat.

    3. Compare API snapshots / test conditions
    1. Select a saved connection with an API key in Settings. Session visibility depends on its permissions.
    2. Start playback yourself. Enter a scenario label and observed network, launch surface and outcome.
    3. Press Capture for each test point. Each capture fetches and saves its own snapshot; no manual snapshot step is required. With several sessions, select the intended one from that fresh response.
    4. Review the differences and export the report before closing. Captures are memory-only, independent of the live snapshot, and do not replace historical server/client logs.
